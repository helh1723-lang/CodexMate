# CodexMate 新手向导

> 读这一份就够。目标是让你在 20 分钟内搞清楚：**面板上每个东西是什么、你该点哪里、什么时候必须你亲自做决定。**

命令示例里的 `codexmate xxx`，在没全局安装时等价于 `npm run cli -- xxx`。

---

## 0. 先建立正确的心智模型

别把它当聊天工具，也别当项目管理工具。它是一条**流水线**：输入是一个 Issue，输出是一个可审查的 Pull Request。

关键一句话：**每个环节都需要你点头，它从不自己决定。**

你在面板上其实只做三件事：

1. **看状态** —— 现在卡在哪一步
2. **做决定** —— 批不批、跑不跑、发不发
3. **交给本机** —— 剩下的 Codex 执行和检查自己跑

它永远不会替你做的事：合并受保护分支、部署、接受来自 Issue / PR 正文的指令。这些是硬边界，不是"暂未实现"。

## 1. 面板地图：8 个页面各回答一个问题

| 页面 | 回答什么问题 | 你什么时候来 |
|---|---|---|
| **团队总览** | 现在整体什么情况？ | 每天开工第一眼 |
| **任务看板** | 每个任务卡在哪一步？ | 干活时待得最久的地方 |
| **审查中心** | 这份代码改得对不对？ | 对方推了 PR 之后 |
| **接力中心** | 对方干不下去，我接着干 | 收到接力申请时 |
| **协作规划** | 目标怎么拆成任务？ | 开始一个新目标之前 |
| **质量报告** | 实际跑了哪些检查？ | 想知道"到底验没验过" |
| **本机审批** | 有什么在等我拍板？ | 看到红点就进来 |
| **工作区设置** | 自动化能替我做到哪一步？ | 第一次配置时 |

每个页面顶部的副标题其实就是它的职责，概括得很准：

| 页面 | 副标题 |
|---|---|
| 团队总览 | 连接彼此的工作，让每一次交接都有上下文 |
| 任务看板 | 从一个明确的目标，到一份可审查的成果 |
| 审查中心 | 以真实 diff 为依据，让每一条反馈可追溯 |
| 接力中心 | 带上代码检查点，把下一步交给队友 |
| 协作规划 | 先对齐目标与依赖，再确认开始 |
| 质量报告 | 看见实际执行的检查，保留未验证的边界 |
| 本机审批 | 每个写入动作，都由你作出明确决定 |
| 工作区设置 | 让自动化按照你的规则运行 |

## 2. 看板上的 8 个状态（最重要的一张表）

任务只有这 8 种状态。看懂这张表，看板就彻底不迷糊了。

| 状态 | 卡面显示 | 含义 | 谁在等 | 你该做什么 |
|---|---|---|---|---|
| `ready` | 待开始 | 任务已就绪，还没启动 | 你 | 认领后点「启动 Codex 任务」 |
| `needs_approval` | 待审批 | 有**某个具体操作**卡在审批队列 | **你** | 去「本机审批」确认或拒绝 |
| `running` | 进行中 | 本机 Codex 正在跑 | 机器 | 不用管，想看细节就点日志 |
| `review` | 待审查 | 草稿 PR 已建好，等人审 | 对方 | 你去审，或者催对方 |
| `blocked` | 已阻塞 | 检查失败，或被前置任务挡住 | 你 / 依赖 | 去质量报告看哪项挂了 |
| `handoff_pending` | 待接力 | 检查点已推送，等接手者接受 | 接手者 | 接受方的活 |
| `done` | 已完成 | PR 已合并、Issue 已关闭 | — | 收工 |
| `cancelled` | 已取消 | 被撤销 | — | 无 |

### 最容易搞混的三个

- **`待审批` 不是"任务需要批准"**，而是「某个具体操作需要你批准」。而且**要在「本机审批」页面操作，不是在卡片上点**。
- **`已阻塞` 有两种原因**：检查失败、或前置任务没完成。看卡片下方的说明区分，处理方式完全不同。
- **`待接力` 不是任务失败**，是对方主动把上下文交出来了。

## 3. 卡片上的小标记

| 标记 | 意思 |
|---|---|
| `#25` | Issue 编号，对应 GitHub 上的原始 Issue |
| `高优先级` / `常规` / `低优先级` | 任务优先级 |
| `待分配` / 头像 | 负责人 |
| `N 项检查` | 这次运行实际跑了几个检查 |
| `N 项依赖` | 有几个前置任务必须先完成 |

## 4. 依赖图怎么读

看板下方是**任务依赖图**：

- **箭头方向 = 前置任务 → 后续任务**，箭头起点必须先完成
- 灰掉的节点 = 前置没完成，现在启动不了（"依赖未完成时阻止启动"）
- 显示"还没有任务依赖" = 所有任务互相独立，随便挑一个开始

### 冲突预警比依赖更要命

黄色提示条长这样：

> `#24 与 #26 可能同时修改 src/search，建议串行处理或先对齐接口。`

这表示两个任务会碰同一批文件，**同时干必然冲突**。看到这条就串行做，或者先跟对方把接口对齐再动手。依赖图是"顺序"问题，冲突预警是"撞车"问题，后者不处理会真的产生合并冲突。

## 5. 从头到尾走一遍（第一次实战）

### 第 0 步 · 体检

```bash
codexmate doctor
```

四项必须全绿：Node ≥ 22.13、Git、`gh auth login`、`codex login`。额度会显示「未知」—— **这是设计，它不猜测官方没暴露的值。**

### 第 1 步 · 先玩演练，别碰真实仓库

```bash
npm run demo
```

演练工作区**不调用 Codex、不写入 GitHub**，用独立数据库。把上面第 2、3 节的每个状态都点一遍，比读文档快十倍。

### 第 2 步 · 连接真实仓库（你，Owner）

```bash
codexmate init /path/to/repo
```

会预览并创建四样东西：`.codexmate/config.yml`、Issue 模板、`.gitignore` 条目、`cm:*` 标签。**需要你确认**。

⚠️ **然后必须提交并推送到默认分支**，否则对方 `join` 时会找不到配置：

```bash
git add .codexmate && git commit -m "chore: 加入 CodexMate 协作配置" && git push
```

接着编辑 `.codexmate/config.yml`，把 `members`（成员 + 角色 + 可改路径）和 `workers`（每个成员当前活跃的设备 ID，来自 `doctor`）填好，再提交一次。

### 第 3 步 · 对方加入

```bash
codexmate join /path/to/repo
```

会核验他的 `gh` 账号、仓库权限、`origin` 是否与绑定仓库一致。**角色取"配置里写的"和"GitHub 实际权限"的下限** —— 本机配置无法给自己提权。

### 第 4 步 · 日常循环（这才是你以后每天干的）

```
① 协作规划 → 生成 AI 拆分草案 → 人工核对 → 确认创建 Issues
② 看板    → 认领任务 → 启动 Codex 任务
③ 审批页  → 确认执行          ← 这一步必须有，跳不过去
④ 等运行结束 → 自动跑检查
⑤ 检查通过 → 推送分支并创建草稿 PR
⑥ 对方    → 审查中心 → 启动只读 AI 审查 → 人工核对 → 发布审查评论
⑦ 有意见  → 按审查意见修复（最多 2 轮，防止无限循环）
⑧ 人按仓库规则合并 → Issue 关闭 → 解锁依赖它的任务
```

**②③⑤⑦ 是四个需要你操作的节点，其余是自动的。**

### 第 5 步 · 干不下去了怎么办

对方额度耗尽、或者单纯想换人接手：

```
卡住的一方 → 接力中心 → 推送检查点并申请交接
接手的一方 → 接力中心 → 检查并接受 → 从精确 SHA 新开自己的线程
```

交接包里固定有六项：**目标、验收完成情况、精确 SHA、剩余任务、风险、已实际跑过的检查**。

⚠️ **不会迁移原来的对话线程。** 接手的人用自己的 Codex 新开线程，带着这六项继续。这是设计而非缺陷 —— 因为两人的账号和额度是独立的，本来就不该共用线程。

## 6. 那些数字到底是什么意思

面板上最容易让人发懵的就是各种数字。逐个拆开。

### 团队总览的四个数字

| 数字 | 含义 |
|---|---|
| 进行中的任务 | 本机 + 团队正在跑的 |
| 等待审查 | 有草稿 PR 等人看 |
| 等待接力 | 处于 `handoff_pending` 的任务数 |
| 待你确认 | 审批队列里有几条等你拍板 |

### 工作区状态那几个词

| 显示 | 含义 |
|---|---|
| 本机 / 演练数据 | 当前数据来源 |
| 最近同步成功 | 上次成功拉到 GitHub 状态的时间 |
| 等待同步核验 | 还没同步过，数据可能不是最新的 |
| 未调用 · 演练模式 | 演练环境，没有真跑 Codex |
| 额度未知 | 官方没暴露这个值，工具不估算 |

### 质量报告的数字（这页最需要看懂）

- **「真实记录，不做自评分」** —— 只统计本机真实跑过的 Run 和检查结果，没有主观打分
- **已记录运行 / 实际检查 / 检查通过 / 检查失败** —— 本机可追溯的统计，**不代表整个团队**
- **「未运行的检查不会计入通过率」** ← 这句是关键。所以看到"通过率 100%"，**要同时看"实际检查"那一列**，很可能只跑了两三项
- **建议优先回归的检查** —— 只有在有真实失败证据时才会出现，没失败过就是空的

### 审批的「有效至」

审批**15 分钟后过期**，并且绑定三样东西：**任务版本、内容摘要、本机策略**。

任何一样变化，旧审批立刻失效。所以你没法"提前批好放着"—— 必须用的时候再批。这是防止审批变成橡皮图章的设计。

### 工作区设置的四个数字

| 设置 | 含义 |
|---|---|
| 轮询间隔（秒） | 多久检查一次 GitHub 上的新变化 |
| 任务超时（分钟） | 单次 Run 超过多久判定为超时 |
| 最多修复轮次 | 按审查意见修复的轮数上限，默认 2，防止无限循环 |
| 日志保留（天） | 过期日志会被清理，**工作树与历史记录会保留** |

## 7. 三个开关：默认全关，新手别急着开

位置在「工作区设置 → 执行与审批策略」，注意它标注了 **仅作用于此仓库 / 此设备**。

| 开关 | 默认 | 开了会怎样 |
|---|---|---|
| 自动启动分配给我的低风险任务 | **关** | 前台 Worker 可以启动本人任务。依赖、设备和权限检查仍然生效 |
| 自动推送并创建草稿 PR | **关** | 自动执行完成且扫描通过后，推分支建草稿 PR。**不会合并或部署** |
| 本机协作通知 | 开 | 任务、审批、接力与失败通知在工作台去重展示 |

**新手建议：前两个先别开。** 手动跑通几轮，等你彻底清楚每一步在干什么再开。开了也只省掉"点启动"和"点推送"这两下，审批流程一步都不会少。

即使全部打开，下面这些仍然永远不会自动发生：**合并、部署、接受来自 Issue/PR 的指令。**

## 8. 新手最容易踩的 6 个坑

1. **`init` 之后忘了提交** → 对方 `join` 直接报错。`.codexmate/config.yml` 必须在默认分支上才生效。
2. **以为审批放着也没事** → 15 分钟一到旧审批作废，得重新发起。
3. **看到"通过率 100%"就放心** → 去看"实际检查"那一列，没跑的检查根本不计入分母。
4. **改了代码还想用旧审批** → 内容摘要变了，审批自动失效。这是保护机制，不是 bug。
5. **两人同时改同一批文件** → 看板下面那条黄色冲突预警不是装饰，看到就串行处理。
6. **指望接手的人继续你原来的对话** → 不会。他新开线程，交接靠的是那六项检查点。

## 9. 出事了怎么办

| 现象 | 做什么 |
|---|---|
| 服务起不来 | `codexmate doctor` 逐项排查 |
| 运行中断了 | `codexmate recover` 对账中断的本机运行 |
| 磁盘占满了 | `codexmate prune` 清理过期日志（保留工作树与历史） |
| 想知道某次运行干了啥 | `codexmate logs <issue>`（输出始终脱敏） |
| 完全不想碰 GitHub | `npm run demo` 演练模式 |
| 状态显示"同步中断" | 当前显示的是缓存数据，等网络恢复后重新同步即可 |

## 一句话总结

**面板是给你做决定用的，不是给你干活的。**

看到 `待审批` 就进审批页拍板，看到 `已阻塞` 就去质量报告找原因，看到冲突预警就串行处理，剩下的交给本机跑。
